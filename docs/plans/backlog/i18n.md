# Plan: Full i18n pass

**Status:** proposed · part of [Backlog plans](README.md)
**Written:** 2026-11-26

## Problem

`TODO.md` ("Full i18n pass") asks for every user-facing string to be wrapped
in `__()` and translated into the twelve locales the profile page offers, and
estimates 2–3 days of mechanical work plus translator cost, deferred until the
English copy is locked.

Measured against the code, three things are off:

- The job is bigger than 2–3 days. There are roughly 2,200 unwrapped string
  sites, not a few hundred (counts below).
- The language preference is stored but has almost no effect. The middleware
  that applies it is not on the Filament panels' middleware stack, so even a
  fully translated app would render English on a normal page load.
- Two of the twelve offered locales (`no`, `fr_CA`) have no Filament
  translations at all, so users who pick them get English Filament screens
  even after our own strings are done.

"Defer until the copy is locked" is right for the translation spend. It is
not a reason to defer the wrapping, the plumbing, or a CI check that stops
the count from growing. If those wait as well, every month adds more
unwrapped strings.

## What exists today (checked in code)

**Locale select.** It is on the Profile page, not the Security page:
`app/Filament/Auth/EditProfile.php:37-42` (`Select::make('locale')`), with
options hard-coded in `localeOptions()` at `:129-145`: `en es fr fr_CA de nl
pt it da sv no fi`. The docblock at `:120-127` already says every label is
still hard-coded English. The value is stored in `users.locale`
(`app/Models/User.php:49`), and `User::displayLocale()` falls back to
`config('app.locale')`.

**Applying it.** `app/Http/Middleware/ApplyUserPreferences.php:29-38` calls
`app()->setLocale($user->locale)`. It is appended to the `web` group only
(`bootstrap/app.php:83-90`). The three panel providers each declare their
own middleware list without that class:
`app/Providers/Filament/AdminPanelProvider.php:260-276`,
`OperatorPanelProvider.php:219-236`, `PortalPanelProvider.php:96-113`.
Filament registers panel routes with that list, not the `web` group
(`vendor/filament/filament/routes/web.php:27-28`:
`->middleware($panel->getMiddleware())`), so full panel page loads don't
apply the preference. Livewire's update endpoint
does run the `web` group, so after the first interaction a page can switch
language halfway through. The route file makes the first half certain. The
Livewire half is inferred, and the first test below pins both down before
anything else is built.

**`lang/`.** One file: `lang/vendor/filament-panels/en/resources/pages/create-record.php`,
a published Filament override that changes one string ("Create & create
another" → "Create & add another"). There is no `lang/en/*.php`, no JSON
file, and Laravel's own `validation.php`, `auth.php`, `passwords.php` and
`pagination.php` are not published. The framework ships those in English
only (`vendor/laravel/framework/src/Illuminate/Translation/lang/en`).
`config/app.php:81-85`: `locale` and `fallback_locale` both default to `en`.

**Filament's own translations.** `vendor/filament/filament/resources/lang`
has 64 locales. Of our twelve, ten are covered. `no` is missing because
Filament uses `nb`, and `fr_CA` is missing with no fallback to `fr`: Laravel
falls back to `fallback_locale` (`en`), not to the parent language.
`pt` and `pt_BR` both exist.

**Existing `__()` use.** 163 calls in `app/` and `resources/views/`. All but
seven are in Jetstream scaffolding views (`resources/views/profile`, `teams`,
`api`, `navigation-menu`), plus 7 in `resources/views/emails`, 6 in
`app/Actions` and 1 in `app/Filament`. The product's own UI is effectively
0% wrapped.

  (`:372-385`), both multilingual models.
- The persona prompt scaffolding in
  `app/Services/Flows/AgentFlowCompiler.php:802-830` is English
  instructions to the model. It is not caller-facing copy.

**SMS.** STOP/HELP/START replies come from the carrier's sender pool
(`app/Jobs/ProcessInboundMessageJob.php:161-164`). Outbound bodies are
written by operators or the AI. The app owns almost no SMS copy of its own
today.

## Goal

1. A user's language choice is applied on every request on every panel, and
   in the mail and notifications sent to them.
2. Every user-facing string Orbital owns goes through the translator, under
   a stable key, with English in `lang/en/`.
3. CI fails when a change adds an unwrapped user-facing string or a key with
   no English value, so the count only goes down.
4. Translation is bought per area once that area's English is locked, and
   client-facing areas come first.
5. Callers hear the client's language, not the operator's: AI personas and
   the platform's own prompts have a language.

Out of scope: RTL. None of the twelve locales is right-to-left. If Arabic,
Hebrew, Persian or Urdu is ever added, `dir="rtl"` and a Tailwind logical-
property audit become their own plan. Also out of scope: translating content
users write themselves (scripts, personas, directory entries, messages).

## Design

### Locale plumbing (phase 0, before any wrapping)

- Add `ApplyUserPreferences` to all three panels' `->middleware([...])`
  lists, after `StartSession`/`AuthenticateSession` so `Auth::user()`
  resolves. Keep it in `web` as well for non-panel routes.
- Fix the locale codes:
  - Store `nb` for Norwegian and keep accepting `no` as an alias. A one-off
    migration rewrites existing `no` rows.
  - Use `Translator::determineLocalesUsing()`
    (`vendor/laravel/framework/src/Illuminate/Translation/Translator.php:508`)
    to give the fallback chain `fr_CA → fr → en` and `pt_BR → pt → en`.
    That lets `fr_CA` reuse Filament's `fr` strings, and lets us ship
    `fr_CA` as a thin override file of the Québec-specific terms.
- Move the locale list out of `EditProfile::localeOptions()` into
  `config('orbital.locales')`. Each entry is `code => [native name, enabled]`.
  The select shows only enabled locales, and a locale is enabled only when
  its `lang/{code}` set is ≥95% complete (the checker below reports this).
  Until then the select offers English only. Showing twelve languages that
  all render English is worse than showing one.
- `User` implements `Illuminate\Contracts\Translation\HasLocalePreference`
  and returns `displayLocale()`. Mailables and notifications sent to a user
  then render in that user's locale automatically.
- Add `teams.locale` (nullable, defaults to the platform locale). It is the
  client's language: used for mail and SMS to people who aren't users
  (on-call contacts, forwarded messages, invitation emails before the user
  exists), and as the default for that client's personas and audio prompts.
  It is edited next to `teams.timezone`.
- Publish Laravel's `validation`/`auth`/`passwords`/`pagination` files and
  take translations of them from the `laravel-lang/lang` package. We don't
  hand-author those.

### Key naming convention

Use structured PHP keys, not English-as-key JSON.

```
lang/en/
  common.php        # Save, Cancel, Delete, Yes/No, status words reused everywhere
  admin/clients.php # one file per admin resource/page: ClientResource → admin/clients
  admin/settings.php
  operator/workspace.php
  portal/messages.php
  portal/calls.php
  mail.php          # subjects + bodies of every Mailable
  audio.php         # caller-facing TTS text (AI fallback, disclosures)
  enums.php         # option labels for model constants (Voice::GENDER_OPTIONS, Skill::CATEGORIES…)
```

Key shape: `{panel}/{area}.{section}.{element}[.{attribute}]`, in snake case.
For example:

- `__('admin/clients.form.answer_phrase.label')`
- `__('admin/clients.form.answer_phrase.helper')`
- `__('portal/messages.table.caller')`
- `__('mail.voicemail_received.subject', ['caller' => $caller, 'duration' => $d])`

Rules:

- Placeholders are always named (`:caller`), never built by concatenation.
  That rules out patterns like `'Use system default ('.config(...).')'` at
  `EditProfile.php:41`.
- Plurals use `trans_choice()` with Laravel's `{0}|{1}|[2,*]` syntax. Fixed
  sentence fragments are never pluralised by appending `s`.
- A string used in more than one panel goes in `common.php` only if it means
  the same thing everywhere. "Status" on a call and "Status" on an operator
  may translate differently, so they get separate keys.
- Enum and option labels live in one place (`enums.php`), keyed by the
  stored value. Models expose them through a `label()` helper so Filament
  selects and table badges share one translation.
- Implicit Filament labels: set `translateLabel()` globally with
  `Field::configureUsing()` / `Column::configureUsing()` in a service
  provider only as a stopgap. That makes the auto-generated English label
  the key. The wrapping pass then gives each field an explicit keyed
  `->label(__())`.

Why not JSON English-as-key: these screens change often. With JSON, every
copy edit changes the key and orphans its translations silently. With
structured keys, an English edit keeps the key, and the stale-translation
check below catches the drift. The cost is that the English text isn't
visible at the call site. The IDE's Laravel plugins resolve that, and
`lang/en` is the reviewable copy deck.

### Extraction tooling and the CI check

Add a scanner, `php artisan orbital:i18n-scan`, built on `nikic/php-parser`.
It is already installed (`vendor/nikic/php-parser`) but only as a transitive
dependency, so promote it to `require-dev`. Blade files are compiled with
`Blade::compileString()` and the compiled PHP is parsed the same way, plus a
text-node pass over the template for literal HTML copy.

It reports:

1. **Unwrapped literals:** a string literal containing a letter, passed as
   the first argument to a configured list of methods (the list from the
   count above). Also string-literal static `$title`/`$navigationLabel`-style
   properties, and Blade text nodes.
2. **Unknown keys:** an `__('x.y')` with no value in `lang/en`.
3. **Unused keys:** keys in `lang/en` that nothing references. This is a
   warning only, because dynamic keys exist.

Allow an exemption with a trailing `// i18n-ignore` or a Blade
`{{-- i18n-ignore --}}` for things that aren't copy: log lines, config
values, test fixtures, `resources/views/asterisk/`, and brand names.

**Baseline mode.** `--baseline=lang/.i18n-baseline.json` records today's
unwrapped sites by file, method and string, not line number, so the baseline
survives unrelated edits. CI runs `orbital:i18n-scan --baseline=… --fail-on-new`
in `.forgejo/workflows/application-tests.yml`, next to the Pint step at
`:84-87`. A PR that adds an unwrapped string fails. A PR that wraps strings
must shrink the baseline, and the scan rewrites the baseline file when run
with `--update-baseline`. This step is what lets wrapping start before
translation and stay done.

**Translation checker.** `php artisan orbital:i18n-check` reports per locale
and per file:

- **Missing:** keys present in `en` but not in the locale.
- **Stale:** the `en` value changed after the translation was made. The
  checker tracks this with `lang/.source-hashes.json`, which records a hash
  of the English text each translation was made from.
- **Completeness %:** this drives `config('orbital.locales')`'s enabled
  flag.

It doesn't fail CI by default. It fails only for a locale marked enabled
that drops below its threshold.

Off-the-shelf packages (string exporters, translation managers) were
considered. None of them knows Filament's fluent label methods, which are
two thirds of the job. The scanner is a few hundred lines and is the part
that has to be right, so we write it ourselves.

### The "copy locked" gate

Wrapping is never gated. Only buying translations is.

A translation area is one `lang/en/{file}.php`. It is **locked** when all
three of these hold:

1. **No open plan rewrites it.** The screens it covers aren't the subject of
   an unshipped plan in `docs/plans/` (for example
   `is-parity/03-message-model` reshapes portal messages, so `portal/messages`
   can't lock before that plan ships).
2. **It has been quiet for 30 days.** `git log --since=30.days -- lang/en/{file}.php`
   shows no changes to existing values. New keys are fine: they get
   translated in the next batch.
3. **Someone signed off.** The product owner has read the file as a copy
   deck. Reading the `lang/en` file, not the screens, catches tone and
   consistency problems once instead of in twelve languages.

The lock is recorded in `lang/LOCKS.md`: area, date, and who signed off.
Changing a locked string is still allowed. The change is a normal PR, and
`orbital:i18n-check` then reports that key as stale in every locale, which
becomes the next translation batch. Locking doesn't freeze the code. It
marks the point where changing copy starts to cost money.

### Translator workflow

- **Tool.** Self-hosted Weblate, or the contractor's TMS if the translators
  bring one. Weblate is open source, reads and writes Laravel PHP
  translation files directly, keeps translation memory, and shows
  translators the screenshots and context comments we attach. Do not email
  spreadsheets around. That loses the stale-tracking.
- **Context.** Every key in `lang/en` that is shorter than ~4 words, or
  ambiguous, gets a `// context:` comment saying where it appears and what
  it refers to, for example "column header; the caller's phone number".
  The scanner warns when a new short key has no context comment.
- **Batches.** One batch per locked area per locale. Translations come back
  as a PR from the Weblate integration branch. A native-speaker reviewer
  approves each locale, ideally one of NCI's bilingual operators for `es`
  and `fr_CA`. CI runs `orbital:i18n-check`.
- **Glossary first.** Before batch 1, agree a ~50-term glossary per locale:
  message, call, client, operator, queue, on-call, script, persona,
  disposition. Answering-service vocabulary is domain-specific, and
  inconsistency between screens is the most common translation defect.
- **Cost control.** Translate the client-facing areas into the locales a
  real client actually asks for, starting with `es` and `fr_CA`. Translate
  admin and operator screens only for languages an operator team actually
  works in.

### Pluralization, dates, numbers, timezones

- **Plurals:** `trans_choice()` everywhere a count is shown. That replaces
  the 7 ternaries and the `Str::plural` in the 2FA banner. Laravel's
  pluralizer handles the CLDR forms for these European locales, and Finnish
  and the Scandinavian languages need nothing special beyond `one`/`other`.
- **Dates:**
  - Use Filament's per-table and per-schema default display formats, set
    from a locale-to-format map in a service provider. For example `en`:
    `M j, Y g:i A` and `de`: `d.m.Y H:i`.
  - Replace the 38 hand-written `->format()` calls with
    `->translatedFormat()` using those map entries, or `isoFormat('LLL')`,
    which Carbon localises.
  - Relative times (`diffForHumans`, 6 sites) are already localised by
    Carbon once the locale is set.
- **Numbers and currency:** `Illuminate\Support\Number::format()` and
  `::currency()` take the locale through intl. `ExpressionEvaluator`'s
  `formatnumber` keeps its explicit `Fixed` and `Comma` styles, which
  script authors pick on purpose, and gains a `Locale` style.
- **Timezones:** these are independent of locale and already modelled. Set
  `FilamentTimezone::set(auth()->user()?->displayTimezone())` in
  `ApplyUserPreferences` once it runs on panels. The 16 per-column
  `->timezone()` closures can then go, except where a column deliberately
  shows the *client's* zone (`ViewEmailThread.php:83-100`).

### Client-facing surfaces first

In order. Each item is a lockable area.

1. **Client portal** (`app/Filament/Portal`, `resources/views/filament/portal`):
   about 45 PHP strings and a handful of Blade strings. This is the only
   panel clients see, and it's small enough to finish in a day.
2. **Mail to clients and invitees.** `app/Mail/*` and `resources/views/emails`,
   `resources/views/mail`, `resources/views/invitations`, about 30 strings
   plus subjects. Mail to a user uses `HasLocalePreference`. Mail to a
   non-user address uses the client's `teams.locale`, set with
   `Mail::to(...)->locale($team->locale)`.
3. **Auth screens** (`resources/views/auth`, ~45). Clients log in through
   these.
4. **SMS copy Orbital owns.** Today that is close to none. When features
   from `is-parity/05` or `16` add system-generated texts, such as dispatch
   notices, check-in prompts or secure-message links, they go into
   `lang/en/sms.php` from day one and render in the client's locale. Keep
   SMS strings GSM-7-safe in translations where possible. An accented
   character can force UCS-2 and halve the segment length, which costs real
   money. Make `orbital:i18n-check` warn when a translated SMS string leaves
   GSM-7.
5. **Caller-facing audio.** This depends on the *client's* (or DID's)
   language, never the operator's.
   - `AiFallbackPrompt::DEFAULT_MESSAGE` and the disclosure and voicemail
     renderers take text from `lang/{team locale}/audio.php`. The rendered
     files gain a locale segment in their spool path.
   - The stock Asterisk prompts at `from-trunk.blade.php:132` need the
     matching Asterisk sound packages in `docker/asterisk/` and
     `Set(CHANNEL(language)=…)` in the client dialplan. Only do this when a
     non-English client exists. Until then, record a TTS rendering through
     `AiFallbackPrompt` instead.
6. **AI personas.**
   - Add `agent_personas.language` (BCP-47, defaults to the team locale).
     The compiler adds one instruction line, "Speak only in Spanish unless
     the caller asks otherwise". Keep the rest of the scaffolding in
     English: it is instructions to the model, and models follow English
     instructions fine while answering in the target language.
   - The worker passes the language to STT: Deepgram's `language` and
     ElevenLabs Scribe's language code (`agent.py:388-402`). Pinning the
     language noticeably improves accuracy over auto-detect on 8 kHz
     telephony audio.
   - **Voices: yes, per-locale voices are needed in practice.** The TTS
     models are multilingual, but a voice designed for English speaks
     Spanish with an English accent, and callers notice. The persona's
     voice picker filters `Voice` by `language`, which the column already
     supports.
   - A bilingual line is two personas, one per language, chosen by DID or
     IVR choice. This matches `is-parity/26-skills-based-routing.md`'s
     "Spanish line" model. Switching language mid-call is out of scope.

Admin and operator panels come after these, area by area, as each area
locks.

## Edge cases

- **Locale changes mid-session.** Saving the Profile form should redirect so
  the whole page re-renders in the new language. Otherwise the Livewire
  partial updates mix languages.
- **Queued jobs and the scheduler** have no authenticated user. Anything
  they render (mail, notifications, TTS) must pass the recipient's or team's
  locale explicitly. `HasLocalePreference` covers notifiables, and the
  `->locale()` call covers everything else. Add a test per Mailable.
- **Broadcast and Reverb payloads** that carry display text, such as toast
  titles pushed to operators, must be rendered per recipient, or carry a key
  and parameters that the browser looks up. Prefer sending keys.
- **Strings stored in the database**, such as seeded intake-goal names,
  persona templates or availability reasons, are content, not UI. Leave them
  in the seeding language, and mark them for per-locale seed variants only
  where a client sees them.
- **Search and sort** over translated enum labels: filter on the stored
  value, never on the label.
- **Fallback visibility.** A missing key falls back to English silently.
  In non-production environments, log missing keys through
  `Lang::handleMissingKeysUsing()` so QA sees them.
- **String length.** German and Finnish run 30–40% longer than English.
  Check the operator workspace's dense layouts (`MultiCallWorkspace`) in
  `de` before enabling it for operators.
- **Implicit labels and the stopgap.** Once `translateLabel()` is on
  globally, a field named `name` has the key "Name". Explicit keys from the
  wrapping pass replace those over time. The scanner should flag a
  remaining implicit label as unwrapped.

## Rollout

**Phase 0: plumbing.** About 1 day. Not gated on copy.

- Middleware on the panels.
- `nb`/`fr_CA` fallback chain and the `no` → `nb` data fix.
- `config('orbital.locales')`, with the select limited to complete locales.
  Today that means English only.
- `HasLocalePreference`.
- `teams.locale`.
- Published framework lang files from `laravel-lang/lang`.

**Phase 1: scanner and baseline in CI.** About 2 days. Not gated.

- `orbital:i18n-scan`, `orbital:i18n-check`, and the baseline file.
- CI step. From this point, new code arrives wrapped.

**Phase 2: wrapping.** About 7–9 days. Not gated. It can run in parallel
across areas and slots in between feature work, one PR per area. Order:

1. portal
2. mail
3. auth
4. common/enums
5. operator
6. admin pages
7. admin resources, with `ClientResource` last since it changes most
   often

Each PR shrinks the baseline. This phase also does the plural, date and
number conversions for the files it touches.

**Phase 3: translation.** Gated per area by the lock.

- Glossary.
- Weblate project.
- `es` and `fr_CA` for portal, mail, auth and audio first.
- Enable a locale in the select once its client-facing areas are complete.
  Admin and operator screens follow per locale only on demand.

**Phase 4: caller-facing language.** Gated on a real non-English client.

- `agent_personas.language`.
- STT language passing.
- The voice filter.
- Localised fallback and disclosure audio.
- Asterisk sound packs, if needed.

## Tests

- **Feature test:** a user with `locale = 'es'` loads `/portal`, and the
  response has `<html lang="es">` and a Filament chrome string in Spanish.
  This fails today, and confirms the middleware finding.
- **Livewire test:** a profile save with a new locale redirects. The next
  request renders in the new locale.
- **Unit tests:**
  - The locale fallback chain (`fr_CA` key missing → `fr` value; `fr`
    missing → `en`).
  - `no` is accepted and normalised to `nb`.
- **Per Mailable:** sending to a user with `locale = 'fr'` renders the
  French subject. Sending to a bare address on a team with `locale = 'es'`
  renders Spanish.
- **Scanner tests** (fixtures under `tests/Fixtures/i18n`):
  - Detects a literal `->label('Foo')`, a static `$title`, and a Blade text
    node.
  - Ignores `__()`, `i18n-ignore`, and `resources/views/asterisk`.
  - Baseline matching is line-number independent.
- **Checker test:** changing an `en` value marks the matching `es` key
  stale.
- **Phase 4:** the persona payload from `AgentPersonaController` includes
  `language`. A worker unit test confirms it reaches STT construction.

## Open questions

- Which locales to actually offer. `TODO.md` raises Polish, Ukrainian,
  Russian and Québec French. Filament covers `pl`, `uk` and `ru`. Let actual
  client demand decide, not the scaffolding list. For NCI specifically,
  Spanish and Québec French are the likely first two.
- Do we want per-client portal language (from `teams.locale`) to override a
  portal user's own preference? Probably not: the user's choice should win.
- Translator budget and vendor: professional agency, freelancers through
  Weblate, or bilingual staff with professional review?
- Should the Asterisk stock prompts be replaced entirely with
  TTS-rendered prompts from `lang/*/audio.php`? That would give one source
  of truth per language and drop the sound packages.

## Size

- Phases 0–2 (plumbing, scanner, all wrapping): about **2 weeks** of
  engineering. That is the real number behind the TODO's "2–3 days".
- Phase 3: per locale, ~2,000 short strings (~12–15k words) for the full
  app, or ~150 strings for the client-facing set alone. Engineering time is
  small, and the spend is translator cost.
- Phase 4: about 3–4 days, once a non-English client exists.
