# Plan: Release and install readiness

**Status:** proposed · part of [Backlog plans](README.md)
**Written:** 2026-11-26

## Problem

`TODO.md` has three sections of open items that each stand between Orbital
and being something a stranger can find, install and trust:

- **"Before making the repository public."** Covers the CLA mechanism, a
  security contact, `ORBITAL_SOURCE_URL` per environment, and the `docker/`
  secret re-sweep with its history-rewrite decision.
- **"First-run gaps found while writing the VKE runbook."** A Helm install
  has no login, and nothing at install time says how to create one.
  `orbital:make-admin` misbehaves without a terminal.
- **"Runtime config not yet set."** A missing Anthropic key is discovered
  only when an AI job fails.

The first section is written as if the repository were still private. It
isn't:

- `https://git.calltheory.com/calltheory/orbital` answers anonymously, and
  the Forgejo API reports `private: false` (repo created 2026-04-29).
- `https://github.com/CallTheory/orbital` is a public read-only mirror,
  created 2026-09-21, with one public fork.

Both serve `docker/asterisk/manager.conf`, `docker/livekit/livekit.yaml` and
`docker/livekit/sip-config.yaml` byte-identical to this checkout, with the
committed AMI secret, LiveKit API secret and Valkey password in them. All
three were checked on 2026-11-26 by comparing sha256 of the raw files. Those
values have been in history since the first commit (`a59d27a`, 2026-04-13).

So this plan is no longer "what to do before going public". It is: fix what
is already exposed, then finish the items that make the public repo safe to
contribute to and to install from.

  timestamp (`routes/api.php:49`).
- There is no first-run checklist anywhere in the app.

## Goal

1. No credential that works against a running system is in the public
   repositories, and CI blocks the next one before it merges.
2. A stranger can find the security contact, encrypt a report, and get a
   reply. The repo, the website and each deployment agree on where to send
   it.
3. Every deployment's `/source` points at the source it is actually
   running, down to the commit.
4. Contributions can be accepted without anyone tracking CLA signatures by
   hand.
5. A fresh `helm install` tells the installer how to log in. Creating the
   first admin works unattended, never blocks, and never puts a password on
   a command line.
6. A missing AI provider key shows up in `orbital:status` and on the
   dashboard before traffic needs it. When traffic does hit it, the thread
   goes to a human instead of failing silently.

## Design

### 1. Committed secrets: rotate, don't rewrite

**Rotate.** This is §3/§4 of `security-review-fixes.md`:

- Generate the AMI secret, LiveKit key/secret and Valkey password at
  bootstrap into `.env`.
- Template the three `docker/` files, or have them read env.
- Stop publishing 5038 and 7880 on `0.0.0.0`.
- Release notes tell every Compose operator to rotate. Any Compose stack
  started from an unmodified checkout has these values and should be
  treated as compromised if 5038 or 7880 were reachable.
- `DefaultCredentials::shipped()` (`app/Support/DefaultCredentials.php:31-40`)
  gains the three old values as known-bad, so `orbital:status` flags a stack
  still running them.

**History rewrite: recommend no.** Reasons:

- The values are already public on two forges, in at least one fork
  (`lma-bsp/orbital`), and in any clone, CI cache or GitHub event archive
  made since April. A rewrite removes them from *our* copy only. It does
  nothing for anyone already holding them. Rotation is the only real fix,
  and once rotated the old values are worthless.
- A rewrite changes every commit hash since `a59d27a`. That breaks:
  - signed tags and Cosign signatures over released artifacts
    (`application-tests.yml:500-560`);
  - `ORBITAL_COMMIT` deep links baked into every released image;
  - the cross-repo tagging in `docs/release/cross-repo-tagging.md`;
  - every fork and open PR.
- Rewrite only for something rotation can't fix: customer data, personal
  data, or a credential to a third party that can't be revoked. The
  full-history scan below decides whether any such thing exists. If it
  does, use `git filter-repo` on a fresh mirror clone, force-push to
  Forgejo, re-mirror GitHub, contact GitHub support to purge cached views,
  and notify fork owners. That is a separate, deliberate change with its own
  announcement.

Record the decision and the scan result in `SECURITY.md` under a short
"Past exposures" note, so a researcher who finds the old values in history
knows they are rotated and not worth reporting.

### 2. Secret scanning in CI (gitleaks)

Use **gitleaks**: a single static binary, fast on PR diffs, and the same
download-and-checksum-verify pattern the workflow already uses for trivy
(`application-tests.yml:370-384`). trufflehog's live-verification mode is
useful for the one-off history audit. It is a poor fit for PR gating
because it phones out to the services it finds keys for.

- **New job `secrets`** in `application-tests.yml`. It runs on every push
  and PR, needs nothing else, and fetches with `fetch-depth: 0`:
  - On PRs: `gitleaks git --log-opts="origin/main..HEAD" --redact --exit-code 1`.
  - On main: `gitleaks dir . --redact` on the working tree.
- **Config `.gitleaks.toml`** at the repo root:
  - Extends the default ruleset.
  - Adds a rule for 40–64-char hex values on `secret|password|api_secret`
    keys in `*.conf` and `*.yaml`. Those are the shapes that slipped
    through.
  - An allowlist for vetted placeholders: `APIorbitaldev` as a public key
    prefix, `changeme`, `password` in `.env.example`, and test fixtures.
    Each allowlist entry has a comment, the same discipline as
    `.trivyignore.yaml`.
- **Baseline.** Run once over full history with
  `gitleaks git --report-path` before turning the check on. Every finding
  gets classified: rotated (the `docker/` three), dev-only (the localhost
  edge key), or false positive. All of them go into a
  `.gitleaks-baseline.json` passed with `--baseline-path`, so the job only
  fails on new findings. Any finding that is real *and* not rotatable
  triggers the rewrite path in §1.
- **One-off history audit.** Also run
  `trufflehog git file://. --only-verified` over full history and over the
  GitHub mirror. This catches a live third-party key that gitleaks
  classifies generically. The result is recorded in the PR that adds the
  job.
- **Pre-commit (optional, documented in `CONTRIBUTING.md`):**
  `gitleaks git --pre-commit --staged`.

### 3. CLA mechanism

Keep the CLA. CONTRIBUTING's relicensing promise, and the
"including proprietary terms" clause in `CLA.md` §4, need a grant that the
DCO (`Signed-off-by`) doesn't give.

**Mechanism.** A Forgejo Actions workflow, `cla.yml`, triggered on
`pull_request` and `issue_comment`:

1. It looks up the PR author's Forgejo username in `.cla/signatures.json`,
   which holds `{username, name, email, cla_version, signed_at, pr_url}`.
2. **If the author is listed:** it sets a commit status `cla/signed` =
   success.
3. **If not:**
   - It posts one comment with a link to `CLA.md` and the exact phrase,
     and sets `cla/signed` = pending.
   - When the author comments the phrase, the workflow appends them to
     `signatures.json` through the API, as a commit to `main` by a bot
     account with a narrow token, and flips the status to success.
4. **Co-authors** from `Co-authored-by:` trailers are checked the same
   way. The phrase must come from each person.
5. **Exemptions:** maintainers and bots (Renovate,
   `noreply@anthropic.com` trailers on maintainers' own PRs) via an
   allowlist in the workflow.
6. **Branch protection** on `main` requires `cla/signed`.

This beats CLA Assistant and the other SaaS bots, which are GitHub-only.
Our PRs land on Forgejo, and the GitHub mirror takes none. A
`CLA.md` version bump forces re-signing by comparing `cla_version`.

**Corporate CLA:** none for now. CONTRIBUTING already says to describe the
fix instead if an employer forbids signing.

### 4. Security contact and security.txt

- **Pick one address.** Either create `security@calltheory.com` as a
  monitored alias, or change `SECURITY.md` to the address security.txt
  already lists. Prefer `security@`: it is conventional, it can be filtered,
  and it routes to whoever is on call for it. Send a test message from
  outside and get a reply before calling this done.
- **PGP:**
  - Generate a dedicated key for the security address, with a 2-year
    expiry and an offline primary key.
  - Publish it at `https://calltheory.com/.well-known/pgp-key.txt` and on
    `keys.openpgp.org`.
  - Add `Encryption: https://calltheory.com/.well-known/pgp-key.txt` to
    security.txt.
  - Fix `SECURITY.md:11-12` to say the key is linked *from* security.txt,
    and print its fingerprint inline, so a reader can verify the key
    against two sources.
- **security.txt fields:**
  - `Contact:` must match SECURITY.md.
  - Add `Policy: <link to SECURITY.md on the forge>`.
  - Keep `Expires` under a year. Today it is 2027-08-12, which is fine.
  - Sign the file with the same key (clearsigned, as RFC 9116 allows).
  - Add a calendar reminder to renew `Expires` and the key.
- **Per-deployment security.txt.** Each Orbital install is run by a
  different operator, so the app should serve its own:
  - New route `GET /.well-known/security.txt`, public and cacheable, next
    to OIDC discovery at `routes/web.php:196`.
  - It renders from two new Platform Settings: `security.contact` (an
    email or URL) and `security.policy_url`, plus an `Expires` computed at
    now + 180 days.
  - If `security.contact` is unset, it returns 404 rather than pointing a
    deployment's users at Call Theory. Upstream is the right place for bugs
    in Orbital, not for an operator's compromised install.
  - The About page links it.

### 5. `ORBITAL_SOURCE_URL` per environment

The rule: whoever builds the image owns the source URL. Make that
mechanical rather than a thing to remember.

- **Build-time default.**
  - Add `ARG ORBITAL_SOURCE_URL` to `Dockerfile:69-77`, baked into
    `ENV ORBITAL_SOURCE_URL`. Runtime env still overrides it.
  - The release workflow passes the canonical URL.
  - `deploy/build.sh` and any local build script pass `git remote get-url`
    of the remote the commit was pushed to, and always pass
    `ORBITAL_COMMIT=$(git rev-parse HEAD)`.
- **Refuse to lie at runtime.** `orbital:status`, and a dashboard health
  check (`licensing`, category `Platform`), warn when either of these
  holds:
  1. `ORBITAL_COMMIT` is empty. A source offer without a commit is a guess.
  2. The source URL is still the upstream default and the build's version
     isn't a tagged upstream release (`Release::channel()` is `dev`, or the
     version is not a semver tag). That combination means modified code
     pointing at unmodified source.
- **Helm.** Every `values-*.yaml` overlay gets an explicit
  `licensing.sourceUrl` line with a comment, so a fork's operator sees it
  while editing values.
- **This host.**
  1. Push the running branch to a public remote: the fork
     `lma-bsp/orbital` is public, but the 8 commits aren't on it.
  2. Set `licensing.sourceUrl` in `deploy/values-orbital.yaml` to that
     remote.
  3. Rebuild with `ORBITAL_COMMIT`.

  This doesn't wait for any of the code changes above.
- **Environment matrix** (to keep in `docs/admin/licensing` or similar, not
  a code concern):

  | Environment | Builds from | Source URL |
  |---|---|---|
  | Upstream releases | tagged canonical repo | default |
  | Orbital Cloud / Call Theory hosted | canonical repo | default (if unmodified) |
  | Any fork's deployment | the fork | the fork's public URL |
  | Local dev (`sail up`) | working tree | default is acceptable, since there are no external users |

### 6. First-admin path on Helm

**NOTES.txt.** Add a block before "Next:", shown on install only
(`.Release.IsInstall`), plus a one-liner on upgrade:

```
Create the first administrator (a fresh install has no login):

  kubectl --namespace {{ .Release.Namespace }} exec -it deploy/{{ laravel }} -- \
    php artisan orbital:make-admin --name="Your Name" --email=you@example.com

  It prompts for the password. In a script, pipe it on stdin instead:

  printf '%s' "$ADMIN_PASSWORD" | kubectl --namespace … exec -i deploy/{{ laravel }} -- \
    php artisan orbital:make-admin --name=… --email=… --password-stdin

Then sign in at https://{{ .Values.global.domain }}/admin
```

If `firstAdmin.existingSecret` (below) is set, show instead: "The first
admin was created from Secret `<name>`; delete that Secret now."

**Optional unattended path: `firstAdmin.existingSecret`.** This is for
GitOps installs where nobody will exec into a pod.

- A values key that names a Secret the operator creates out-of-band, with
  `email`, `password` and an optional `name`.
- Mounted *only* into the migrate job's seed step as `SUPER_ADMIN_*` env,
  never into the Laravel, Horizon or worker pods. That fixes the problem
  with putting the variables in `app-secrets`.
- `FirstSuperAdminSeeder` already does the rest.
- The password never appears in `helm get values`, because values only hold
  the Secret's name.
- NOTES.txt tells the operator to delete the Secret after first login. The
  seeder is first-install-only through `seed-if-empty`, so the Secret is
  dead weight afterwards.

### 7. `orbital:make-admin` without a terminal

Changes to `CreateAdminUser`:

- **Detect non-interactive up front.** If
  `! $this->input->isInteractive() || ! stream_isatty(STDIN)`, never call
  `ask()` or `secret()`. Instead, if any required value is missing, fail
  immediately with:

  ```
  orbital:make-admin needs --name, --email and a password when there is no terminal.
  Pass --password-stdin and pipe the password, or re-run with `kubectl exec -it`.
  ```

  Exit with `INVALID` (2). This covers `-n`, `kubectl exec` without `-i`
  (today's bare "Aborted.") and `-i` without `-t` (today's hang).
- **`--password-stdin`.** Reads one line from STDIN and trims the trailing
  newline. It is mutually exclusive with `--password`. Using `--password`
  still works, for compatibility, but prints a warning that the value is
  visible in history, process lists and audit logs.
- **`--generate-password`.** Generates a 24-character random password and
  prints it once. It is the alternative for people who'd rather copy a
  password than make one up.
- **Validate before the transaction:** email with Laravel's `email` rule,
  and the password against the same `Password` rule defaults the app's
  password-change form uses. On a validation failure, print the errors and
  exit 2.
- **Align with the seeder.** Extract the user-plus-team-plus-role creation
  into one action, `App\Actions\Platform\CreateSuperAdmin`, that both call,
  so the two paths can't drift. Pick the seeder's "Platform" team and
  `admin` role: its comment explains why. Keep "already exists" as a
  failure.
- **Docs.** Update `first-login.md` and `vultr-vke.md:441-452` to the
  `-it` / `--password-stdin` forms.

### 8. AI provider readiness

Add `App\Support\AiProviderReadiness`, a plain helper like
`DefaultCredentials`, so the CLI and the dashboard share one list.

- **Requirements come from configuration, not a fixed list.**
  `requirements()` returns `provider => [reasons…]`:

  | Configuration in use | Needs |
  |---|---|
  | Any active persona | its `llm_provider` (an empty one means anthropic, per `agent.py:148`) |
  | Any active persona | its `tts_provider` and `stt_provider` (empty means elevenlabs) |
  | Any queue or endpoint routing email or SMS to AI | anthropic |
  | Knowledge stores using OpenAI embeddings | openai |
  | The configured TTS provider of the voicemail-greeting, disclosure and AI-fallback renderers | that provider |
  | Directory smart ingest enabled | anthropic |

  The `local` and Ollama providers need no key. A missing key for a
  provider with no reason listed isn't reported.
- **Status per provider:**
  - `ok` (key set);
  - `missing` (needed and not set: `WARN`, or `DOWN` when the reason is
    live inbound routing that will fail on the next message);
  - `not needed`.

  Optional `--probe`: a cheap authenticated call per provider, such as
  listing models, which reports `invalid key`. It is off by default because
  it costs a network call per provider.
- **Worker env.** The worker falls back to its own env keys
  (`AgentPersonaController.php:66-67`), so Laravel alone can't tell whether
  a voice persona will work. Extend the heartbeat POST (`routes/api.php:49`)
  to carry `{"keys": {"anthropic": true, "elevenlabs": false, …}}`, as
  booleans only and never values. The readiness check counts a provider as
  set if either side has it.
- **Surfaces:**
  - `orbital:status` gains an "AI providers" block after the credentials
    block, using the same `!` lines.
  - Add `--strict`, which exits non-zero on any `DOWN` or `missing` line,
    so install scripts and CI smoke tests can gate on it. The exit code
    stays `0` by default so existing callers don't break.
  - A `SystemHealthService` check `ai_providers` in the existing `AI`
    category puts it on the dashboard.
- **Fail usefully at job time too.**
  - Check `config('services.anthropic.api_key')` before dispatching, in
    `ProcessInboundEmailJob:181` and `ProcessInboundMessageJob:242`. When
    it is missing, don't dispatch: log once per thread, add a
    `ConversationActivity` note ("AI reply skipped: no Anthropic key
    configured"), and leave the thread in the human queue.
  - Inside the jobs, treat "key not configured" as permanent: call
    `$this->fail()` rather than retrying 3 times, and add a `failed()`
    handler that does the same handback for every other failure after the
    last retry.
- **First-run checklist.**
  - A super-admin dashboard widget lists the setup items still open, each
    linking to the page that fixes it:
    - no admin besides yourself (optional);
    - default credentials unrotated (`DefaultCredentials`);
    - AI providers missing (above);
    - `ORBITAL_SOURCE_URL`/commit warnings (§5);
    - `security.contact` unset (§4);
    - no SIP trunk;
    - no client.
  - The widget hides once every item is done or dismissed.
  - `orbital:status` prints the same list, so CLI and UI share one source.

## Edge cases

- **Rotation on running Compose stacks.** Changing the AMI secret needs
  Asterisk and every AMI client restarted together. Changing the LiveKit
  secret invalidates in-flight room tokens. Rotate in a maintenance window,
  and write it up in the release notes.
- **gitleaks false positives** on generated configs (`docker/asterisk/config/version.txt`
  UUIDs), test fixtures and documentation examples. Allowlist each entry by
  path *and* rule, never by path alone. The scan has to stay meaningful for
  `docker/`.
- **CLA bot token.** The bot commits to `main`. Give it a token scoped to
  that repo, and let it touch only `.cla/signatures.json`: branch protection
  with a path rule, or have the bot open a PR it auto-merges.
- **Contributors without a Forgejo account** (patches by email): the
  maintainer records the signature manually in `signatures.json` with the
  email thread as `pr_url`.
- **`--password-stdin` with a TTY:** if stdin *is* a TTY, ignore the flag
  and prompt with `secret()`, so `-it` plus the flag doesn't wait silently.
- **`stream_isatty` is unavailable** on some Windows PHP builds. Fall back
  to `posix_isatty`, and treat unknown as non-interactive. Failing loudly is
  better than hanging.
- **Readiness check with zero personas** on a fresh install: report "no AI
  configured" as informational, not as missing keys. A platform that
  doesn't use AI is valid.
- **Keys set only in env** (`.env`/Secret), not in Platform Settings:
  `config()` already sees them, so they count as set.
- **Source URL behind auth.** If a fork's forge is private, `/source`
  resolves but serves a login page. The `licensing` check should do a HEAD
  request with `--probe` and warn on a non-200 response.

## Rollout

The go-public checklist, in order. Items 1–4 are urgent because the repo
is already public. The rest make it a repo worth contributing to and
installing from.

1. **Rotate and stop committing the three `docker/` credentials.** This is
   [`security-review-fixes.md`](../security-review-fixes.md) §3, §4 and §7,
   in one PR. Release notes tell Compose operators to rotate.
   `DefaultCredentials` learns the old values.
2. **Run the full-history audit** (gitleaks and trufflehog
   `--only-verified`) over Forgejo, the GitHub mirror and the fork. Classify
   every finding. Decide on a rewrite: the default is no, unless the audit
   finds something unrotatable.
3. **Land the gitleaks CI job** with `.gitleaks.toml` and the baseline from
   step 2. Make it a required check on `main`.
4. **Fix the source offer on running deployments.**
   - Push this host's running branch to a public remote and set
     `licensing.sourceUrl`.
   - Rebuild with `ORBITAL_COMMIT`.
   - Audit any other deployment running non-release code the same way.
   This is config only: do it this week.
5. **Security contact.**
   - Create or confirm `security@`, generate and publish the PGP key, and
     update calltheory.com's security.txt (`Contact`, `Encryption`,
     `Policy`, signed).
   - Fix `SECURITY.md`, and add the "Past exposures" note from step 2.
   - Send a test report from outside.
6. **`ORBITAL_SOURCE_URL` build arg and runtime warning** (§5). Add the
   explicit `licensing.sourceUrl` line to every Helm overlay.
7. **CLA workflow** (§3).
   - Backfill `.cla/signatures.json` from comments already made on existing
     PRs.
   - Make `cla/signed` a required check.
   - Update `CONTRIBUTING.md`.
8. **`orbital:make-admin` hardening** (§7) and the shared
   `CreateSuperAdmin` action.
9. **Helm NOTES.txt first-admin block** (§6), using the new flags from

10. **AI provider readiness** (§8): the helper, `orbital:status` block and

11. **Per-deployment `/.well-known/security.txt`** (§4) and the first-run

12. **Rewrite `TODO.md`'s "Before making the repository public" section** to

## Tests

- **`CreateAdminUserTest`:**
  - With `--no-interaction` and no flags: exit code 2 and the guidance
    message, and no user row.
  - `--password-stdin` with piped input creates the user. The stored hash
    verifies.
  - `--password` and `--password-stdin` together are rejected.
  - An invalid email or short password exits 2 and leaves no rows behind.
  - The seeder and the command produce the same team name, pivot role and
    platform role (one test over the shared action).
- **Helm:** a `helm template` snapshot test (or a `helm unittest` case, if
  the chart adopts it) that the install NOTES contain `orbital:make-admin`,
  and that `firstAdmin.existingSecret` mounts only into the migrate job.
- **`AiProviderReadinessTest`:**
  - With no personas: nothing required.
  - A default-provider persona requires anthropic and elevenlabs.
  - An email queue routed to AI requires anthropic.
  - A key set via config counts as ok. A heartbeat reporting the worker key
    counts as ok.
- **`orbital:status`:**
  - The AI block lists missing providers.
  - `--strict` exits 1 when one is missing, and 0 otherwise.
- **Jobs:**
  - With the Anthropic key empty, `ProcessInboundEmailJob` doesn't dispatch
    the agent job and records the activity note.
  - `ProcessEmailWithAgentJob` with an empty key fails once, without
    retries, and runs the handback.
- **`Release`:** the warning fires for a dev channel plus the default URL,
  and for an empty commit. It stays quiet for a tagged release plus the
  default URL.
- **Route test:** `/.well-known/security.txt` returns 404 when unset, and
  RFC 9116 fields when set.
- **CI self-test:** a throwaway branch adding a fake 48-hex
  `api_secret:` line to a YAML file fails the `secrets` job.

## Open questions

- Who owns the security inbox and the PGP key's offline primary key, and
  who is the backup? The response targets in `SECURITY.md` (2 business days
  to acknowledge) need a named person.
- Should the GitHub mirror stay? It doubles the places history lives, but
  it is also where people look. If it stays, add a `SECURITY.md` pointer to
  its repo settings, since GitHub surfaces that file in its security tab.
- Should the NCI fork (`lma-bsp/orbital`) stay public? It has to be public,
  or at least reachable by the deployment's users, to satisfy §13 for the
  NCI deployment. If NCI-specific commits shouldn't be public, the
  alternative is upstreaming them or a separate public source mirror.
- Should `orbital:status` exit non-zero by default once `--strict` has been
  around for a release?
- Is `--probe`'s live key validation worth the outbound calls on every
  dashboard refresh, or should it run only from the CLI?
